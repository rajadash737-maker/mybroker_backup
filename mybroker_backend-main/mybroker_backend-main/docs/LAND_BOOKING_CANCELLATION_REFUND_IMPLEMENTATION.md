# Land Booking Cancellation and Refund Management

## Source audit (before implementation)

- **Booking and listing:** `SellLandBooking` in `app/sell_land/models.py` represents the buyer's booking, links `request_id` and `buyer_id`, and stores the deal price, booking fee, payment status/reference, and registry state. `SellLandRequest.status` blocks/publishes the property; the booking workflow uses `BOOKED`, registry statuses, and eventually listing `SOLD`. `BookingStatus` currently has no cancellation state.
- **Actual payment amount:** `SellLandBooking.booking_fee_amount` is the expected fee, and is a floating point field; it is not sufficient proof of what was captured. The buyer property payment ledger is `RazorpayPaymentOrder` in `app/payments/models.py`. Its verified successful record carries `status=SUCCESS`, `currency=INR`, integer `amount_paise`, and `payment_id`; property order creation derives amount from the booking fee and payment verification/webhooks reconcile it to success. This is the source for eligible refund amount, converted from paise using decimal arithmetic. The deal price in `SellLandBooking.deal_amount` is not the booking payment and must not be refunded by default.
- **Legacy payment caveat:** `/sell-land/buyer/bookings/{booking_id}/pay` calls `mark_booking_paid_for_buyer` and sets `SellLandBooking.payment_status=SUCCESS` from an authenticated client request. It does not establish a captured gateway payment. Cancellation must therefore require a matching `RazorpayPaymentOrder` verified as successful and must not treat booking status alone as evidence of captured funds.
- **Existing cancellation/refunds:** `SellLandRequest` cancellation fields and the Admin/Accounting refund queues are for seller listing/processing-fee cancellations. They do not represent a buyer's property booking cancellation. Site Visit refunds use separate `SiteVisitRefund` and payment context records. Neither is appropriate for land booking refunds.
- **Admin detail:** `GET /admin/sell-land/booked-listings/{request_id}` returns the most recent successful booking and its booking fee/payment status, deal price, buyer, registry details, and listing information. The Admin Android `BookedListingDetailScreen` is the corresponding property details screen. A booking-specific command should address the booking ID and be Super Admin only.
- **Buyer screens:** buyer offers/bookings are represented in `/sell-land/buyer/offers`; the UI's buyer offer card and buyer land details cover offer/booking status. Booking creation/payment are exposed by `/sell-land/buyer/bookings` and `RazorpayPaymentOrder` APIs. There is no booking-cancellation/refund UI or buyer-owned booking refund API yet.
- **Accounting:** the existing Accounting dashboard and `AccountingRefund*` APIs handle seller cancellation refunds. They expose seller UPI and must remain separate from property booking refunds. The new land booking refund queue needs its own model, endpoints, authorization, and Android section.
- **Authorization and audit:** existing Admin routes use role dependencies; buyer booking reads are ownership-scoped; Accounting and Super Admin are distinct roles. Existing property booking state has no cancellation/refund audit history. Site Visit refund code is a reference for manual external refund processing only, and will not be reused.
- **Migrations:** repository head before this implementation is `20261117_0046_site_visit_completion_audit_event`. No booking-refund table or migration is present. Screenshots were not included alongside the pasted request in the accessible attachment directory.

## Implementation status

### Behavior and API

- Added `BookingStatus.CANCELLED` and a distinct `PropertyBookingRefund` ledger with a unique booking constraint, unique transaction reference, amount/decision checks, and `PropertyBookingRefundEvent` history. The migration is `20261117_0047_property_booking_refunds`, based on `20261117_0046_site_visit_completion_audit_event`; it has **not** been applied.
- Cancellation preview: `GET /admin/sell-land/bookings/{booking_id}/cancellation-preview`. Cancellation: `POST /admin/sell-land/bookings/{booking_id}/cancel`. Both are Super Admin only. Cancellation is limited to active booked/registry-pending statuses and a successful, INR, property-context Razorpay payment that matches buyer, listing, and the booking's payment reference. The default refund is the captured `amount_paise / 100`; a custom amount must be positive and no greater than captured funds. No Refund records a zero payable amount.
- Cancellation and refund states commit with booking status and audit events. The listing returns to LIVE only from BOOKED and when there is no other active booking or unrelated offer lock. Completed registry/sold states are ineligible. Database row locks plus a unique refund-per-booking constraint guard duplicate/concurrent cancellation attempts.
- Buyer reads: `GET /sell-land/buyer/bookings/{booking_id}/refund`; UPI submission: `POST /sell-land/buyer/bookings/{booking_id}/refund/upi`. Both are CUSTOMER only and owner scoped. UPI IDs are validated and AES-GCM encrypted under the separate `LAND_BOOKING_REFUND_ENCRYPTION_KEY`; only the Accounting queue/detail endpoints decrypt them. Buyer responses and notifications never include UPI.
- Accounting endpoints: `GET /admin/sell-land/accounting/property-booking-refunds` (pending queue; `include_history=true` returns history), `GET /admin/sell-land/accounting/property-booking-refunds/{refund_id}`, and POST `.../{refund_id}/confirm` or `.../{refund_id}/fail`. Only active ACCOUNTING users can access/process them. The queue and detail show buyer UPI only to Accounting. Confirmation requires the exact approved decimal amount and a unique transaction reference; repeating the same confirmation is idempotent. The app records a manually completed external transfer and does not initiate payment.
- Accounting's property booking queue is separate from existing seller-cancellation and Site Visit refund records. The buyer offer response now includes the owned booking ID and safe cancellation/refund summary so Android can show cancellation reason, decision, amount, status and confirmation details.
- Notifications cover cancellation, UPI receipt, Accounting readiness, confirmation and failure. Delivery failures are caught after committed state changes and cannot reverse the ledger transaction.

- Admin Android Accounting dashboard links to a distinct Property Booking Refunds queue/detail screen with buyer UPI, history, confirmation, and failure actions. The existing Site Visit Refunds entry remains separate.
