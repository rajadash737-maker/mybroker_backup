The existing uncommitted implementation adds:

- `GET /site-visits/field-officer/my-visits`: requires an active FIELD_OFFICER through the existing `require_roles` dependency; selects only successfully paid rows whose `assigned_field_officer_id` equals the authenticated user; returns an empty array when there are none. ## Refund-details HTTP 503 investigation and fix (2026-11-16)

- Root cause: `POST /site-visits/{booking_id}/refund-details` encrypts the submitted UPI with AES-GCM using `SITE_VISIT_REFUND_ENCRYPTION_KEY`. The observed 503 is emitted when `_key()` raises `RefundEncryptionConfigurationError` because the configured key is missing or invalid. The runtime-secret documentation requires exactly 64 hexadecimal characters (32 bytes). In the local backend environment inspected for this task, the loaded setting was absent (length zero). This confirms a missing local runtime secret; no production configuration was accessed.
- The router deliberately suppresses exception chaining (`from None`) and the repository contained no captured request traceback, so there is no traceback to inspect. The exact application exception and its configuration cause are identified from the endpoint's catch and key loader; production-side presence/format cannot be verified under the no-production-access restriction.
- Backend fix: key parsing now accepts only exactly 64 hexadecimal characters, and the service rolls back the active SQLAlchemy transaction if encryption configuration fails. The API returns a safe, actionable 503 explaining that the booking remains cancelled and refund details are still required. It does not include the submitted UPI or configuration value. The existing refund case remains `pending_details` with no ciphertext and can be retried after the secret is configured.
- Idempotency remains one refund case per booking. After the first successful UPI submission, repeating the endpoint returns that same refund ID/status without replacing details or adding another history event. Details submission only advances the refund to `pending`; it does not mark payment as refunded or confirmed.
- Buyer Android now maps the refund encryption 503 to the same safe actionable explanation. A cancellation succeeds independently, remains visible as cancelled, and its refresh message preserves the failed refund-details explanation; the My Site Visits refund form remains available for retry. The entered value is not cleared on a failed request, and no UPI value is logged or returned in normal buyer responses.
- Regression tests cover the missing-key failure and intact retryable refund case, successful retry with a dedicated non-production key, AES-GCM encryption/decryption round trip, repeat submission idempotency, and refund state/history. The Android error-message unit test was updated but not run (Android Gradle/tests are excluded by request).
- Focused backend SQLite command: `C:\conda-envs\mybroker\python.exe -m pytest -q -p no:cacheprovider tests\test_site_visit_accounting_refunds.py` — **4 passed, 3 dependency warnings**.
